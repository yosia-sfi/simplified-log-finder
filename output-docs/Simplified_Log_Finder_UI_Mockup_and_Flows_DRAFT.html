Simplified Log Finder: UI mockup and flows

DRAFT from Inception package v1.0 (gate approved 2026-11-26) All data below is synthetic. Layout and wording are proposals, not final UI.

What we want to build

A web page where a BA, QA or FE/Mobile developer types a request the way they write it in chat, checks the filters the Finder understood, and gets a readable log from Loki (and, later, the database) without pinging an engineer. It sits in front of the existing sources; Grafana, the database and k9s stay as they are for engineers. Pilot: BCAS, UAT first, then RC. Production is out of scope.

Design rules that shape every screen

  1. Filters are always visible as editable chips. A sentence only fills in chips; nothing runs until the user confirms (Req 6, 10).
  2. Every search has a bounded time window. Vague times ("tadi") are proposed and confirmed first (Req 7, 9).
  3. Times are WIB on screen, UTC to the sources; the raw view keeps the original timestamps (Req 8).
  4. The simplified view is parsed by rules, not by an LLM (Req 15).
  5. Raw view is one click away and keeps every field (Req 17).
  1. Masked by default in every view and copy; unmask and True_Raw only for users with the right, per project and environment, always audited (Req 19, 20).
  2. The internal LLM sees only the sentence, the project dictionary and identifier types; never log content (Req 10.3).
  3. Clear "nothing found" vs "source failed", with a way to widen the window or ask an engineer (Req 14).
  4. The only shareable link is the Escalation_Link, which re-checks the viewer's access (Req 25).
  5. Every search and sensitive action is audited (Req 26).

Business flow

Who does what, from "I need a log" to a readable log, a copy for a ticket or client, or an escalation. Read left to right.

Today versus with the Finder

Today (from the 24 sampled chats)
  1. BA/QA/developer posts a request in team chat ("minta log … jam … CIF …").
  2. An engineer stops work, opens Grafana, the database or k9s.
  3. The engineer finds and pastes the log, often asked again for the same thing.
  4. The requester reads or forwards the log to the client.
With the Finder
  1. The requester signs in and types the same sentence, or sets filters.
  2. The Finder shows editable chips; the requester confirms the time window.
  3. The Finder queries Loki read-only and shows a masked, readable log.
  4. The requester copies it, or asks an engineer with one link when stuck.

Technical flow

One Go (Echo) service in a modular monolith with a React front end on the same origin, PostgreSQL for the Finder's own data, a separate inference VM for the internal LLM, and read-only connectors to the existing Loki and database. Source: design.md v1.0.

D. Raw view, copy and True_Raw

  1. Result opens as masked Simplified_View. "Raw" shows the pretty-printed masked line, original timestamps kept; the open is audited.
  2. Copy buttons show whether the copy is masked or unmasked; each copy is recorded with its type (simplified, raw masked, raw unmasked, True_Raw).
  3. The masking toggle and True_Raw appear only when an unmask grant exists for this project and environment (GET /results/{id}/true-raw checks the right again).
  4. For True_Raw the line is fetched again from Loki using the stored line reference; the audit entry is written before the response; nothing is cached.
  5. A new search or a new session switches masking back on.

What this mockup does not decide

  • Final visual design, wording (Indonesian vs English labels) and responsive behavior.
  • Raw and simplified view details until a masked log sample exists (V-10).
  • Database lookup screen: shown only as an enabled or disabled source; the template picker is not designed (D-03 pending).
  • Grafana Assistant and image input: deferred, not in the MVP.
  • Parameter values (windows, caps, timeouts) are proposals until the Loki spike.
